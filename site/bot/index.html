umi crawler

If you found this page in your server logs, this is the page that answers it.

umi is a web crawler that builds a public, openly licensed index of the web. Everything it collects is published as open data under open-index on Hugging Face. The code is at github.com/tamnd/umi and it is run by Tam Nguyen.

Requests come from one user agent, on every request, at every tier:

umi/1.0 (+https://umi.dev/bot)

Make it stop

The robots token is umi. Nothing else. Not umibot, not umi/1.0, not a prefix of the user agent string. Put this in your robots.txt and umi stops within 24 hours, which is how long a cached robots.txt lives:

User-agent: umi
Disallow: /

If you already block User-agent: *, you already block umi. There is no flag anywhere in umi that ignores robots.txt, and there never will be.

To stop it now, or to stop it across the whole fleet including machines other people run, email tamnd87@gmail.com with the domain. You get an answer from a person within one business day and the block is applied within one hour of a valid request. Send the domain and, if you have them, a few log lines so the request can be matched against what actually happened.

A block is permanent, it is on the record, and it also removes what has already been collected from the next revision of the published corpus. The list of blocked domains is published in open-index/umi-meta, so anyone using an older snapshot can honour it too.

Is it really umi

Anybody can put a string in a user agent header, so there are three ways to check, in order of how easy they are to run.

1. Reverse DNS, forward confirmed

This is the same check that verifies Googlebot and Bingbot, and your tooling probably already does it. Take the address from your log, look up its PTR record, and check the name ends in umi.dev. Then resolve that name and check it comes back to the address you started with. Both halves have to pass. The first half alone proves nothing, because a PTR record is set by whoever owns the address.

$ dig +short -x 62.171.131.190
fetch-3.umi.dev.
$ dig +short fetch-3.umi.dev
62.171.131.190

2. The published address list

Every address umi crawls from is published at umi.dev/bot/umi.json. It is the same shape as Google's googlebot.json, field for field, so a reader that already eats that file reads this one unchanged. The one extra field is name, which carries the reverse DNS name for the range, and a reader that does not expect it ignores it.

AddressReverse DNS name

Traffic from anywhere else claiming to be umi is not umi. When an address changes, the list gains the new one before any crawling moves to it, and the old one stays on the list for a full crawl cycle after the move, so a log line from yesterday still checks out. An address that is retired for cause comes off immediately and this page says when and why.

3. Web Bot Auth signatures

Requests from machines that umi operates are signed under RFC 9421 HTTP Message Signatures, following the Web Bot Auth protocol draft. The signature covers @authority, @method, @path and the Signature-Agent header, and it is good for sixty seconds. The public keys are Ed25519 and are published as a JSON Web Key Set at https://umi.dev/.well-known/http-message-signatures-directory. Keys rotate quarterly with an overlap window, and a rotated key keeps its entry and gains an expiry rather than being deleted, so a request signed last year can still be checked this year.

Signing is built and the directory goes live with the first coordinator operated crawl outside our own domains. Until it does, the two checks above are the ones to use. Rotations are announced here.

Machines run by volunteers sign with their own keys and point Signature-Agent at a separate directory of active fetcher keys, so you can tell a machine we run from a machine somebody else runs, and rate limit them differently if you want to.

Slowing it down without blocking

umi backs off on its own. A slow response, a 429, a 503 or a connection error all widen the gap between requests for that host, and the gap only narrows again after sustained fast responses. Nothing goes below a 200 ms gap for any host, and no host ever sees more than 5 requests per second from the entire fleet.

  • Crawl-delay in robots.txt is honoured, clamped to between 0.1 and 300 seconds. It is not part of RFC 9309, but it is widely deployed and umi obeys it.
  • Retry-After is honoured exactly, in both the seconds form and the HTTP date form, up to 24 hours.
  • A 429 or a 503 multiplies the current gap by four, immediately.
  • Everything under one registrable domain shares a cap of 20 requests per second, so a site with thousands of subdomains does not get thousands of times the traffic.

If a path is expensive to serve and the rest of the site is fine, a Disallow on that path is the precise tool and umi will keep the rest.

What umi collects

Only what is needed to build an index of what a page says.

  • The URL, the final URL after redirects, and the status code.
  • The main content of the page, converted to markdown, with navigation, boilerplate and scripts removed.
  • Outbound links and their anchor text.
  • Title, description, headings and the usual social metadata.
  • Response headers that matter for caching and content type, such as ETag, Last-Modified, Content-Type and Content-Language.
  • Timing, size, which tier fetched it, and digests of the content.

It does not store Set-Cookie, Authorization, Proxy-Authorization or WWW-Authenticate. There is no flag, allowlist entry or operator setting that changes that. It does not collect mailto: addresses from pages, deliberately, because harvesting email addresses at web scale creates an obligation this project does not want.

umi fetches nothing behind a login, solves no CAPTCHAs, bypasses no challenge, and uses no residential proxies and no proxy rotation. It crawls from the addresses listed above and nowhere else. Pages that require an account are pages umi does not have.

What umi publishes

Everything, openly. Crawled pages are converted to Parquet and uploaded to public datasets under open-index on Hugging Face, usually within ten minutes of being fetched, after which the local copy is deleted. The local disk is a cache and nothing else. Manifests are hash chained and signed so a stranger can verify that a published corpus is the one that was produced.

Each published row carries the crawl purpose and the fetch tier that produced it, so a consumer can filter on either.

Purpose

umi has one purpose and declares it: building a public, openly licensed web index.

  • It does not train models on the corpus.
  • It does not browse on a user's behalf as an agent.
  • It does not resell access to anything it collects.

The honest part that most crawler pages leave out: the corpus is open, so other people can and will train on it, and that is outside our control. Saying otherwise would be the dishonest version. If you do not want your site in an open dataset that anyone can download, the block above is the answer and it is meant to be used.

If umi ever gains a second purpose it gets a second user agent, a second key and a second robots token, because a purpose declaration is only worth anything if it is granular enough to act on.

The same declaration in machine readable form is at umi.dev/bot/purpose.json.
